所有算子都是抽象的概念层或者说是一个逻辑规格，它们都要绑定具体的实现。但是这种规格与实现的分离，对于普通用户是透明的。即普通用户只需要调用算子，而不需要关心算子真正实现的方法，以及底层是调用什么样的 kernel 。

vLLM里面有些算子比较特殊，比如 attention backend 后端算子。

# 1. 抽象算子与正式后端

attention 算子是 vLLM 里面有 <u><b>正式后端</b></u> 的抽象算子。
所谓的算子，就是一种逻辑规格，是抽象的。但是一般的算子这层抽象，用户是没有感知的，直接调用就可以，算子内部 dispatcher 会自动选用具体实现。但是 attention 算子不一样，用户能感知到它使用的是不同的算子实现，`FlashAttention`, `FlashInfer`, `XFormers`等等。还可以由第三方提供新的算子实现。所以 attention 算子在用户眼里就是一个抽象算子。这里的“抽象”指的是用户能感知它的抽象，能知道到背后使用的不同实现。普通算子，用户感知不到抽象。但“抽象的逻辑框架”是所有算子的特性，算子架构就是 「规格与实现分离」。更具体的分为「接口 / 实现 / kernel」

## ◼︎正式后端

atttention 是有正式后端的算子
<u><b>正式后端(backend)</b></u>: 指的是算子把内部 "选择哪个实现" 做成一个有名字，有统一接口，可显示指定，可枚举的机制，而不是藏在算子内部的隐藏分支。正式后端通常具备以下特性：

>- <b><u>有统一接口/抽象</b></u>: 框架定义了一个 后端算子 backend 的接口规范，该提供哪些方法(vLLM 里有 attention backend 的抽象定义),各实现都按这个接口来,所以能互换。
>- <u><b>可枚举、有名字</b></u>:`FLASH_ATTN`、`FLASHINFER`、`TRITON`、`XFORMERS` ——每个后端是一个具名选项,能被列出来。
>- <u><b>可显式选择</b></u>: 用户能用 `VLLM_ATTENTION_BACKEND=FLASHINFER` 配置指定。框架也有自动选择的逻辑。
>- <u><b>可回退</u></b>: 选不中或不支持当前 arch 时,按规则退到另一个。

# 2. 算子实现的三种方式：可插拔，可选择，默认绑定

## ◼︎算子实现的三种方式

vLLM 中的算子实现，可以分为三类

第一类：该类算子提供正式后端，具体的算子实现，可枚举，有名字。框架提供一部分选择，另一部分可由第三方提供用户能够选择要使用的实现。这类算子我们称为可插拔。这个算子的实现和可插拔完全暴露给用户。(vLLM 中的 attention 算子就是这一类)

第二类：该类算子提供正式后端，具体的算子实现，可枚举，有名字。框架提供了几个实现，用户只能在这里面选择，不可以放入第三方实现。只提供了开关，可以供用户选择。

第三类：该算子没有正式后端，只有内部分派。算子实现，没有具体名字。内部按 arch/dtype 走不同 codepath,但**没有具名后端、没有统一 backend 接口、不可显式指定**。它有"多 codepath",但没有"正式后端"。

第一类是完全可插拔的算子，目前主要是三个，attention，quantization, MoE。
第二类可选择实现的算法，包括通信后端，KV Cache, CUDA graph等，虽然不允许第三方可插拔，但是框架提供了几个实现可以选择，比如通信后端可选择 NCCL/all-reduce。
第三类完全由框架提供，是实现写死的算子。框架提供的算子直接绑定实现，不能改变。但是内部kernel可以根据 arch/dtype 选择不同的 codepath。比如 RMSNorm 这样的算子, 它的功能比较单一，保留多个实现，收益不高。

上面算子实现的三种方式，分别叫做 「可插拔、可选择、默认绑定」。

> 大多数普通算子，都是框架提供算子时附带提供的唯一实现，并默认绑定，是写死的算子，不能更改。且实现的大部分逻辑都是和直接调用 GPU 计算有关，即算法直接在 kernel 中实现。因此，有时我们也会把 kernel 实现直接说成算子的实现。但是其实是算子的实现运行时调用kernel。

## ◼︎一个算子的多个实现

算子选用，可插拔，可选择，还是默认绑定方式，完全取决于「框架的工程选择」, 不是机制问题。

<u><b>原理层面</b></u>：算子是一个逻辑规格, 实现与规格分离,所以"任何算子的实现原则上都可替换"，这是"算子/实现"这个抽象本身就蕴含的。没有哪个算子在原理上被钉死成只能有一种实现。

<u><b>框架层面</b></u>：某个算子**实际上**暴不暴露可替换的后端、给不给你换、留几个候选,是 vLLM 的**工程决策**, 而不是算子原理。

框架在考虑一个算子是否值得维护多个实现版本的时候一般会考虑

>- 这个算子是不是性能热点、值不值得维护多套实现(attention、GEMM、MoE 是大头, 所以养了很多后端; RMSNorm 收益小,一套够了)
>- 有没有成熟的第三方实现可接(FlashAttention 这种社区生态)
>- 维护成本、测试矩阵爆炸程度(每多一个可选后端,arch×dtype 的组合就翻倍)

所以"能不能换"是**有没有人去实现并接进来、框架愿不愿意暴露这个选择**的问题,不是"原理允不允许"的问题。原理永远允许; 框架按收益决定做不做。
# 3. attention 算子 / attention backend

attention算子是常常被拿出来讨论的抽象算子，它具有最高的灵活性。attention算子就是一个抽象的正式后端。框架提供的算子实现，都可枚举，有具体的名字，比如，`FLASH_ATTN`、`FLASHINFER`、`TRITON`、`XFORMERS`。用户能用 `VLLM_ATTENTION_BACKEND=FLASHINFER` 配置指定, 框架也有自动选择逻辑。另外，它还允许第三方提供的 attention 算子实现接入。因此，它是可插拔的。

注意，attention 本身是一个算子，而`FLASH_ATTN`、`FLASHINFER`、`TRITON`、`XFORMERS`这些都是 attention 算子的实现, 并且这些实现是有名字的。因此 attention 算子是有正式后端的。这些实现就统称为 「attention backend」。

> attention 算子所有有名字的实现，统称为 attention 算子的后端，即 attention backend。

每个后端实现，都会根据不同的 arch 提供不同的 kernel 版本。因此，`FLASH_ATTN` 可能会有sm_80, sm_86, sm_89等 kernel 版本。`XFORMERS`可能支持 sm_75, sm_86 等。也就是说算子实现内部，也会根据 arch/dtype 进行不同 codepath的选择。

同时，attention 算子还接受第三方提供的后端实现，让其成为 attention backend 中的一员。第三方实现的 attention 后端算子，与其他 attention backend一样，可以随时插拔到 attention 算子上。
