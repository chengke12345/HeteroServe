
vLLM 部署模型的时候，启动有两个重要参数，`max-model-len` 与 `max-num-seqs`, 前者代表最大上下文窗口的长度，后者代表最大模型同时处理的请求数。

# `■`上下文限制 「max-model-len」

### 1. 设置上下文窗口 

`max-model-len` 是设置最大上下文长度。它决定了模型启动之后 vLLM 允许的单条序列的最大长度。调整它的大小，只是让 vLLM 框架对请求进行了限制和过滤，并不会赋予模型更强的上下文处理能力。
单条请求上下文长度超过了 max-model-len，vLLM 就会拒绝请求，返回 `HTTP 400 Bad Request`。vLLM服务本身继续运行，其他请求不受影响。

>注意⚠️：`max-model-len` 是用户输入 prompt 的长度 + 推理结果的总长度。例如 `max-model-len=8192`, 输入 9000 tokens, 那就会返回 400。如果输入 7000 tokens 并要求的最长输出 2000 tokens, 也会被拒绝，总长度超过限制了。所以它的限制是
> `输入token数 + 输出token数 ≤ max-model-len`
> 如果我们输入的 tokens 数量小于 `max-model-len`, 但是模型推理产生的 tokens，加起来超过了 `max-model-len` 限制，框架会在达到上限时，强制停止生成，结束原因就是长度限制。我们不需要提前知道“模型自然生成多长”，框架会根据当前seq长度加上已生成 tokens 数，持续检查是否触碰到 `max-model-len`。 

`max-model-len` <u>长度限制，是 vLLM 框架设置的限制，与大模型本身无关</u>。返回 `HTTP 400 Bad Request` 是 vLLM 框架在请求校验阶段的行为，发现长度超限后就拒绝请求，这个请求不会进入模型推理。不是模型 "看完后拒绝回答"，模型不负责返回 HTTP 状态码。

总结：max-model-len 是 vLLM 框架的限制，与模型能力无关。

### 2. 模型上下文能力

模型自身具有上下文能力限制，主要在于位置编码能否处理更远的位置，以及模型是否学会在这些位置上工作。核心约束是：

>- 学习式绝对位置编码通过有固定大小的位置嵌入表(max_position_embeddings), 超过范围可能直接越界。
>- RoPE 等位置编码通常能在数学上计算更大的位置，但是超过训练范围或适配范围，注意力行为和回答质量会明显退化。能输出文字不代表能正确利用远处信息。

模型自身具有上下文能力限制，这个限制是由模型架构，位置编码以及训练过程共同决定的。它决定了模型在多长的上下文里还能可靠工作。

### 3. KV Cache 限制

KV Cache 和其他运行资源，也会决定硬件能容纳、计算多长的序列。设置了 `max-model-len`，主要影响的是，在当前硬件条件下，可以同时装填多少条漫长请求，即满长请求的并发数量。
例如，一个模型的 KV Cache 缓存池中，最多可以容纳 128k tokens

| max-model-len | 满长并发容量 |
| ------------- | ------ |
| 64K           | 2条     |
| 32K           | 4条     |
| 16K           | 8条     |
| 8K            | 16条    |
| ...           | ....   |

这只是对满长上下文容量上并发数的估计。实际上，过长的上下文即使存得下，也可能慢得难以使用。实际情况，要结合业务，参考模型上下文能力，合理设置上下文窗口。这里只是说明，硬件条件 KV Cache 会限制模型上下文的设置，这个设置会影响整体的并发容量和其他请求的处理。

### 4. 设置上下文窗口 与 模型上下文能力

设置上下文窗口 `max-model-len` 与 模型上下文能力，是两个层面的事情。前者是部署时框架设置的限制，后者模型自身的属性。具体的

>- 「`max-model-len`」： 是部署层面的规则，框架允许单条请求的上限，包含输入和输出。超过这个长度，就会拒绝请求，返回 `HTTP 400 Bad Request`。修改它并不改变模型权重和能力
>- 「模型上下文能力」：是模型能否有效理解这么长的上下文，取决于架构，位置编码(RoPE)，预训练长度，长上下文适配等。超出范围，仍然可能运行，但效果不再有保证。

从原理上来讲，「`max-model-len`」 与 「模型上下文能力」 是相互独立的两个层面限制，没有过多的关系。但 vLLM 默认会参考模型能力，决定配置限制，并且会校验你的设置。

简单说，`max-model-len` 决定 「允许送多长上下文」给模型，模型上下文能力决定「能不能理解好」送过来的上下文。 

### 5.  根据业务配置上下文限制

使用框架部署模型的时候，通常是根据业务需要设置 `max-model-len`, 并不是模型能力多大我们就设置多大。在模型能力范围内，我们要兼顾业务类型与KV Cache 预算(并发容量)的控制。

事实上，`max-model-len`的可以理解为，「框架侧对模型处理请求的防御性设置」。设置比模型能力更小的上限，主要是符合业务请求特点的基础上，防止超长请求进入后，占用大量资源，影响其他服务质量，帮助服务保持稳定。
它是部署层面的长度护栏，但它不单独保证质量与资源安全，范围内的回答也可能出错。

例如：模型上下文能力是 64K，我们为不同的业务场景，就可以配置不同的 `max-model-len`

| 业务场景         | 推荐上下文长度  |
| ------------ | -------- |
| 普通对话、短问答     | 2K - 4K  |
| RAG长上下文，多轮对话 | 8K - 16K |
| 长文档分析        | 32K      |
| 超长文档/代码仓库分析  | 64K      |

所以，我们是根据使用模型的场景来设置上下文窗口 `max-model-len`, 它通常小于模型上下文能力，主要是框架侧的防御性设置，防止不符合业务场景的超长请求进入，占用资源，影响其他服务的稳定与正确。 

# `■` 并发限制 「max-num-seqs」

首先，「模型本身没有任何并发处理能力」，模型就是一些参数权重，它本质上就是一个计算图，唯一能做的就是接受输入 token embedding 向量，然后经过权重输出预测结果向量。它本身不具备任何并发能力，也不具备返回 HTTP 状态的能力。

真正提供并发能力的是，使用模型的部署框架。部署框架是用户和模型间的桥梁，它作为模型的使用工具软件，把模型作为后端，接受用户请求，然后更好的调用模型来为用户服务。

它提供 KV Cache, 请求调度，多并发，加载模型权重等等管理资源的功能，还提供推理计算，比如调用算子来使用模型做 attention 计算等功能。这些都是为了更好的使用模型。

所以部署框架才是真正提供多用户、多线程、高并发，资源调度等功能的组件，模型是后端的参数权重，计算图，被框架调用，为用户服务。

影响一个模型推理服务的并发处理能力的因素有四个，「KV Cache 容量限制」，「框架限制并发数 max-num-seqs」，「框架限制单次调度处理上限 max-num-batched-tokens」,「Continous Batching 与算子并行计算能力」。
### 1.  KV Cache 容量限制

如果 KV Cache 缓存容量一定的情况下，`max-model-num` 设置了单个序列最大长度。那么在最大长度下的 KV Cache 可以容纳的请求数，就是满长请求的最大并发数，因为再多的请求，KV Cache 缓存已经耗尽了，新的请求只能排队等待。上面在 KV Cache 的限制中，已经讨论。

KV Cache 容量 和 `max-model-len` 一起在系统资源上限制了满长请求的并发数量上限。这只是对并发性能的一个粗略估算，因为不是所有请求都会拉满上下文限制，甚至大多数请求都不会拉满上下文限制。所以，对并发性能的影响，它只是其中一个因素。

### 2. max-num-seqs

`max-num-seqs` 是在框架层面，限制了模型同时处理序列(请求)的最大数目，即请求并发数。这是框架提供的并发性能，模型只是被调用的参数权重计算图，本身没有并发功能。

如果有超过 `max-num-seqs` 的请求到达，框架就会把它放入请求队列，等待调度。

>KV Cache 容量限制 与 `max-num-seqs` 一起共同决定了系统的并发性能。KV Cache 缓存池的容量耗尽 或者 达到 `max-num-seqs` 上限，这两个条件达到其中任何一个，都会导致新到达的请求进入请求队列，等待资源释放与调度。这两个因素一起决定了系统并发能力的上限。

注意⚠️：把 max-num-seqs 调大，只是放宽调度上限，不代表系统有更强的并发能力。调大后可能提高总吞吐量，但是可能让每个请求变慢，甚至因为 KV 不足，产生抢占和重算。

### 3. max-num-batched-tokens

`max-num-batched-tokens`，限制了一次调度能处理多少 tokens, 在 decode 时，每条序列通常只新增一个 token。它主要影响的是 Prefill 阶段，一条请求可能要处理多个 token，有可能要在多轮调度才能处理完，这就影响了处理速度。

注意⚠️：`max-num-batched-tokens` 设置的是每一轮调度，所有请求加起来可以处理多少 tokens, 也就是总预算。

### 4. Continous Batching 和 算子并行计算速度

Continuous Batching 的运行，算子内部计算时的并行度，和硬件一起决定系统的吞吐速度。也会影响并发的执行。这是在持续批处理，算子实现，GPU 硬件使用效率这个层面的底层运行效率限制。

注意⚠️：Continous Batching 和算子计算效率通常不会直接限制允许的并发数，但会决定这些并发能以多快的速度往前推进。

### 5. 总结

`max-model-len` 和 KV Cache 容量决定了 KV Cache 资源层面对并发数的限制。`max-num-seqs`是框架层面对模型并发处理数的限制。它们两者共同决定了同时允许存在多少活跃的请求或者序列。KV Cache 容量加上 max-num-seqs 是对系统并发数量的直接限制。

`max-num-batched-tokens` 决定了单次调度最大处理 tokens 数，它使得一个sequence可能要多轮调度才能完成计算，它影响一个 sequence 的计算速度。Continous Batching 和算子并行度运算效率，是在计算底层决定了一个请求的执行速度。

>  所以，前两项是在资源层面直接限制了系统处理请求的并发数，后两者是在计算速度层面影响一个请求完成计算的速度，他们间接影响系统并发处理能力。前两者决定请求能「同时挂多少」, 后两者决定 「挂上后能跑多快」，两个层面，四个因素，共同决定一个部署模型的并发处理能力。
